# 그룹 내 타원 vs 단일 타원 — 회전 방향 불일치 진단 절차

> **증상**: 그룹에 속한 타원과 단일 타원의 **회전 방향이 화면에서 다르게 보이는데**, 로그를 보면 값이 같아서 그쪽 AI가 자꾸 **"같다"고 판정**해버림.
> **이 문서**: "로그가 같다" 판정을 무효화하고 실제 분기점을 찾는 측정 절차.

---

## 1. 원칙 — 화면이 ground truth다

- 눈으로 방향이 다른데 로그가 같다면, 결론은 "같다"가 아니라 **"그 로그 변수는 버그보다 상류(upstream)에 있다"** 이다.
- 오히려 유용한 정보다: 두 경로가 **공유하는 모델 각도값은 같고**(그래서 로그가 같음), 그 값을 **화면으로 바꾸는 경로별 변환에서 갈라진다**는 뜻. → 수색 범위가 "로그 지점 하류"로 좁혀진 것.
- 같은 구조의 전례 2건:
  - `ROTATION_FIX_FINDINGS.md` **Finding #2** — 저장값은 하나인데 guide/bake/commit 변환이 경로마다 달라 어긋남
  - `GROUP_RESIZE_SCREENSPACE_FIX.md` **§5** — 크기 로그를 찍고 "문제없음" 오판 (버그는 안 찍은 변수에 있었음)

> **무엇을 측정하는가가 판정을 가른다. 내부 변수의 일치는 화면 불일치를 반박하지 못한다.**

---

## 2. 결정적 측정 — 내부 변수 말고 "렌더된 기하"를 재라

### "같다"의 정의를 교체
> 내부 각도 변수 비교 금지. **"같다" = 렌더된 기하의 부호 있는(signed) 화면 회전 방향이 같다.**

### 화면 프로브 (render 직후)
```
angleScreen = atan2(majorEndY − centerY, majorEndX − centerX)   // 장축 끝점, 화면 px 기준
```
- 같은 회전 조작 동안 **(그룹 내 타원, 단일 타원) 각각의 ΔangleScreen 부호**를 기록.
- 시각적으로 방향이 다르면 이 부호는 **반드시 다르게** 나온다 — 속일 수 없는 측정.
- [ ] 부호가 다르게 나옴 → "같다" 판정 종료, 3장으로.
- [ ] 부호가 같게 나옴 → 시각 인지 재확인 (다른 요소를 보고 있었는지 — 예: 장축이 아니라 sweep/gradient/텍스처가 도는 방향).

---

## 3. 파이프라인 이분법 — 첫 분기점 = 수정 지점

두 경로(그룹 / 단일) 각각에 대해 **같은 조작 한 번** 동안 단계별로 각도 값·부호를 나란히 로그:

```
[1] intent (드래그 입력)        : groupPath = ___   singlePath = ___
[2] model/commit (저장 각도)    : groupPath = ___   singlePath = ___     ← 아마 여기까지 같음 (현재 로그)
[3] visual 변환 (model→visual)  : groupPath = ___   singlePath = ___
[4] geometry 생성 입력 (bake)   : groupPath = ___   singlePath = ___
[5] 화면 프로브 (2장)           : groupPath = ___   singlePath = ___     ← 여기는 확실히 다름
```

- **처음으로 값(특히 부호)이 갈라지는 단계가 수정 지점**이다.
- [2]까지 같고 [5]가 다른데 [3]·[4]를 안 찍고 있다면 — **로그가 없는 그 구간이 범인**. 계측을 추가하라.

---

## 4. 타원 특이 용의자 (우선순위)

- [ ] **1순위 — ellipse visual↔model 반전 경로의 편측 적용**: 이전에 확인된 사실 — *"ellipse/arc도 visual angle과 model angle 사이에 반전 경로가 남아 있다"*. 이 변환이 **단일 경로에만 적용되고 그룹 경로에는 미적용**(또는 그룹에만 이중 적용)이면, 같은 모델값에서 화면 방향이 반대가 된다. → [3] 단계 로그로 즉시 판별.
- [ ] **2순위 — 그룹 경로의 자식 회전 합성 부호**: 그룹 회전을 자식에 전달할 때(`centroid 기준 회전 + 자기 회전각 갱신`) 타원만 별도 분기(per-shape map 로직)를 타며 부호가 다른 경우. → [4] 단계에서 판별.
- [ ] **3순위 — geometry 생성기의 축 각도 규약 차이**: 타원 path 생성기가 그룹/단일에서 다른 함수를 쓰고, 축 각도의 CW/CCW 규약이 다른 경우.
- [ ] 판별 보조 — **반사 홀짝 카운트**: 두 경로 각각 model→화면까지 Y반사/부호 반전 수를 센다. **홀짝이 다르면 방향 반대** — 그 차이 나는 반사 1개가 범인. (`ROTATION_FIX_IMPLEMENTATION.md` 1장의 방법)

---

## 5. 그쪽 AI에 전달할 지시 (복사용)

> 1. "같다" 판정의 근거로 내부 각도 변수를 쓰지 마라. **렌더 직후 장축 끝점의 화면 각도(atan2, px 기준)** 를 그룹 내 타원과 단일 타원에서 각각 찍고, 같은 조작 동안의 **부호 있는 변화량**을 비교하라.
> 2. 부호가 다르면: intent → model → visual 변환 → geometry 생성 입력 → 화면, **5단계를 두 경로 나란히** 로그하고 **처음 갈라지는 단계**를 보고하라.
> 3. 특히 ellipse의 **visual↔model 반전 경로**가 그룹/단일 두 경로에 **똑같이** 적용되는지 확인하라 (한쪽만 적용이면 그게 원인).
> 4. 기존 로그가 같았던 건 그 변수가 분기점보다 상류라는 뜻이다 — "같다"의 증거가 아니라 **수색 범위를 하류로 좁혀주는 단서**다.

---

## 6. 레퍼런스 대조 (이 저장소)

- 레퍼런스는 단일/그룹이 **같은 회전 규약 하나**를 공유한다: 로컬 atan2 절대각 + 이중 모듈로, 경로별 부호 보정 없음 (`GROUP_TRANSFORM_DESIGN_REFERENCE.md` §5).
- 그룹 회전 시 자식 갱신은 "centroid 기준 회전 + 자기 회전각 갱신" **한 가지 코드**로 모든 도형에 동일 — 타원만 다른 분기가 없다.
- 따라서 레퍼런스에서는 [2]~[5] 모든 단계에서 그룹/단일 값이 일치한다 — 이것이 정상 상태의 기준 형상.

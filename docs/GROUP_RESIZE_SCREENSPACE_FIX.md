# 그룹 리사이즈 앵커 고정 — 화면 픽셀 공간 수정 (적용 가이드)

> **2026-07 현재 구현 주의:** 이 문서는 문제를 추적한 과거 설계를 포함한다. pitch/bearing을 잠그는 결론과 `{rotation, scale}`만 유지한다는 제한은 현재 구현에 적용되지 않는다. 최신 기준은 `PITCH_BEARING_TRANSFORM_IMPLEMENTATION.md`이며, 지면 로컬 OBB + 비파괴 live 2×2 affine + 변환 중에만 카메라 입력 잠금을 사용한다.

> **대상 증상**: 그룹 선택상자의 한 핸들을 드래그할 때 **반대편 변(앵커)이 화면에서 고정되지 않고 밀린다.**
> **결론**: 리사이즈 앵커/스케일을 **렌더링·상호작용과 같은 프레임(=화면 픽셀)** 에서 계산하면 해결. 다른 프레임(mercator 미터/모델 좌표)에서 계산해 화면에 그리면, 카메라가 조금만 회전·pitch돼도 앵커가 화면에서 밀린다.
> 관련: `RESIZE_ANCHOR_ANALYSIS.md`(원인 후보), `RESIZE_ANCHOR_FOLLOWUP.md`(다른 프로젝트 오진 분석), `GROUP_TRANSFORM_ISSUES.md`.

---

## 1. 핵심 원인 — "다른 프레임에서 앵커를 잡았다"

리사이즈 불변식은 **"드래그하는 동안 반대편 앵커 A는 화면에서 한 픽셀도 안 움직인다"** 이다. 이 불변식은 **화면 픽셀 기준**이다.

그런데 그룹 박스를 **북향(mercator) 미터 프레임의 AABB**로 잡으면:

```
미터 프레임: +Y = 북쪽 (mercator y 감소)
화면 프레임: +Y = 아래
```

- 순수 수식으로는 앵커가 완벽히 고정된다 (2-shape 대수 검증: `top 이동 = 0.0000`).
- 하지만 **미터 프레임의 "top(북쪽)"과 화면의 "top(위)"은 카메라가 회전(bearing)/기울면(pitch) 서로 다른 지점**이 된다.
- 결과: 미터 공간에선 고정이지만 **화면에 투영하면 앵커가 밀려 보인다.**

즉, 버그는 스케일 수식이 아니라 **앵커를 계산한 프레임 ≠ 사용자가 보고 조작하는 프레임** 이라는 프레임 불일치다. (회전 버그의 "측정 프레임 ≠ 적용 프레임"과 같은 계열.)

## 2. 수정 — 화면 픽셀 공간에서 앵커·스케일

리사이즈에 관여하는 **박스·앵커·스케일·자식 중심 이동을 전부 화면 픽셀**로 처리한다. 크기(scale)만 모델에 반영한다.

```
onResizeStart(handle):                         // 스냅샷 — 드래그 내내 불변
  box0 = 자식들 화면 정점의 AABB (픽셀)          // {cx, cy, hx, hy}
  dir  = 핸들 방향 (화면축: x=+1 오른쪽, y=+1 아래)
  각 자식: startCenterLngLat, startScale 저장

onResizeMove(pointerPx):
  A.x = box0.cx − dir.x·box0.hx                 // 반대편 변 (픽셀, 고정)
  A.y = box0.cy − dir.y·box0.hy
  sx  = dir.x≠0 ? |pointerPx.x − A.x| / (2·box0.hx) : 1   // 잡은 축만
  sy  = dir.y≠0 ? |pointerPx.y − A.y| / (2·box0.hy) : 1
  각 자식:
    C0   = project(startCenterLngLat)            // 시작 화면 중심
    C'   = A + S·(C0 − A)                         // 픽셀에서 앵커 기준 스케일
    center = unproject(C')                        // 다시 지도 좌표로
    scale  = startScale · S                       // 크기만 모델에 반영

onResizeEnd: commit, 스냅샷 폐기
```

**카메라 평면 고정** — 화면축이 항상 지도 평면과 일치하도록:

```js
new maplibregl.Map({ pitch: 0, maxPitch: 0, /* ... */ });
map.dragRotate.disable();
map.touchZoomRotate.disableRotation();
```

`pitch=0 & bearing=0`이면 픽셀↔미터가 균일 선형이라 `scale·S`(픽셀 유도)가 모델 크기에 정확히 반영되고, 앵커가 픽셀 단위로 정확히 고정된다.

### 왜 이게 맞나
- 앵커 A가 **박스가 아니라 드래그 시작 스냅샷 픽셀**에서 1회 확정 → 드래그 내내 불변(출력→입력 피드백 없음).
- `C' = A + S·(C0 − A)` 는 **A를 부동점으로 하는 아핀 스케일** → `C0 = A`인 점(=앵커 변 위의 점)은 항상 제자리.
- edge 핸들은 한 축 `S=1` → 그 축은 이동 0. corner 핸들은 두 축.
- 잡은 축의 반대편 변에 있는 자식/정점은 **정확히 픽셀 고정**, 나머지는 비례 이동(정상).

## 3. 다른 프로젝트에 적용하는 법 (체크리스트)

프레임워크(2D 오버레이/three.js/canvas) 무관. **"상호작용·렌더 프레임에서 앵커를 잡아라"** 원칙만 옮기면 된다.

- [ ] **리사이즈 프레임 통일**: 그룹 박스 AABB를 **사용자가 보고 클릭하는 좌표(화면 픽셀)** 에서 계산한다. 모델/미터/mercator 프레임의 AABB를 쓰지 않는다.
- [ ] **앵커 = 드래그 시작 스냅샷**: `A = box0.center − dir·box0.half` 를 **pointerdown 시 1회** 확정. 매 프레임 현재 박스에서 다시 읽지 않는다 (피드백 금지).
- [ ] **절대 계산**: 자식 위치 = `A + S·(startPos − A)`. **시작 좌표 P₀ 기준**. 증분(delta) 누적 금지.
- [ ] **축 분리**: edge 핸들은 잡은 축만 `S≠1`, 나머지 축 `S=1`. 스칼라 하나로 양축 균등 스케일(`setScale(s)`) 금지.
- [ ] **크기만 모델 반영**: 위치는 `unproject(C')`로 지도 좌표 환산, 크기는 `startScale·S`.
- [ ] **카메라 평면 고정**: pitch/bearing을 0으로 잠가 화면축과 지도평면 일치. (틸트 지원이 필수면, 앵커를 지면 평면 픽셀 투영에서 잡되 여전히 "화면에서 본 프레임" 기준으로.)
- [ ] **회전 피벗과 구분**: 리사이즈 피벗 = 드래그 반대변. 회전 피벗 = 중심. **두 연산이 같은 transform 함수를 공유하면 피벗 계약이 섞이지 않게 분리.**
- [ ] **검증 3종**:
  - 실험 1 (0° edge): 반대편 변 픽셀 고정, 잡은 변만 이동.
  - 실험 2 (왕복 jiggle): 아래→위→아래로 포인터 복귀 시 **원래 크기·위치 복귀**(스냅샷 절대 계산의 증거).
  - 실험 3 (45° 회전/pitch): 카메라 틸트에서도 앵커가 화면에서 고정.

## 4. 요약 표

| | 버그 (다른 프레임) | 수정 (화면 픽셀) |
|---|---|---|
| 앵커 계산 프레임 | mercator 미터 (북=+Y) | 화면 픽셀 (아래=+Y) |
| 렌더/조작 프레임 | 화면 픽셀 | 화면 픽셀 |
| 프레임 일치 | ✗ (카메라 틸트 시 어긋남) | ✓ |
| 앵커 확정 | 매 프레임 현재 박스 | pointerdown 1회 스냅샷 |
| 위치 계산 | 증분/재계산 | `A + S·(P₀−A)` 절대 |
| 왕복 복귀 | ✗ | ✓ |

**한 문장**: 앵커는 반드시 **사용자가 보고 조작하는 그 프레임(화면 픽셀)** 에서, **드래그 시작 스냅샷으로 한 번** 잡아라. 다른 프레임에서 잡은 앵커는 수식이 맞아도 화면에서 밀린다.

## 5. 검증 함정 — "픽셀 크기 그대로"가 왜 오판을 낳나

> 다른 프로젝트는 **로그까지 찍었는데** "픽셀 크기가 그대로"라서 "문제없음"으로 판단했다. 로그가 있어도 **틀린 변수를 측정하면** 오판은 반박되지 않는다.

핵심: **측정한 값(크기)이 버그가 사는 값(위치/앵커)이 아니다.**

- **크기 ⟂ 위치**: 깨진 불변식은 "앵커의 화면 위치 고정"(위치)인데 width/height(크기)를 쟀다. **크기가 완벽히 보존되면서도 전체가 통째로 평행이동**할 수 있다 — 그게 앵커 미고정 증상이다. 버그가 안 건드리는 변수를 재고 "안 변했다"는 건 논리적 비약.
- **크기는 피벗을 모른다**: `크기 = factor × 원래크기` 가 맞아도 **어느 앵커 기준으로** 적용됐는지는 크기에 안 나온다. 같은 크기라도 중심 피벗(앵커 이동) vs 반대변 피벗(정상)을 크기 로그는 구분 못 한다.
- **동어반복 로그**: edge 핸들은 그 축이 `factor=1`이라 **크기가 그대로인 게 당연**하다. "안 변해야 할 축이 안 변했다"를 확인하는 건 코드가 한 일을 코드가 되읽은 것 — 정작 버그는 옆(위치 드리프트)에 있다.
- **자기참조 비교**: "직전 프레임 vs 현재 프레임 크기"로 찍으면 "이 순간 스케일 안 함"만 뜻한다. 기준이 이미 드리프트한 현재 박스면 자기참조라 항상 "일관돼" 보인다.

### 찍었어야 할 로그
```
startAnchorPx = 드래그 시작 시 반대편 변의 화면 좌표      // 1회 고정
매 프레임: assert( currentAnchorPx ≈ startAnchorPx )     // 진짜 불변식 = 위치
```
또는 왕복(jiggle): 아래→위→아래로 포인터를 시작점에 되돌렸을 때 **크기뿐 아니라 위치까지** 시작값으로 복귀하는가.

> **한 문장**: 크기(버그와 무관한 변수)를 찍고 "안 변했다"고 안심했지만, 버그는 위치/앵커(안 찍은 변수)에 있었다. 회전 버그 때 per-frame factor만 보고 넘어간 것과 같은 실수 — **로그의 유무가 아니라 "무엇을 측정하는가"가 판정을 가른다.**

## 6. 그룹 회전 & 박스 삐져나옴 — 최종 모델

§2의 "화면 픽셀 AABB 박스"는 리사이즈 앵커는 잡았지만 두 문제가 남았다:

1. **회전 시 핸들이 튐**: 박스를 매 프레임 자식들의 **화면 AABB**로 재계산하면, 회전할 때 자식이 호를 그리며 움직여 AABB의 모양·크기가 매 프레임 바뀐다 → 핸들 위치가 요동친다.
2. **자식이 박스 밖으로 삐져나옴**: 박스 half를 선택 시점에 1회 고정하면, 이후 자식(특히 자기 회전이 그룹과 다른 경우)이 스케일되며 고정된 박스를 벗어난다.

### 최종 모델 — "지속 회전각 + tight 도출 박스"

지속 상태는 **그룹 회전각 하나뿐**. 박스는 매 렌더 **"회전된 그룹 로컬 프레임의 AABB"** 로 자식에서 도출한다.

```
지속 상태: groupRotation (숫자)        // 선택 SET이 바뀌면 0으로 리셋

매 렌더 박스 도출:
  center = 자식 중심들의 centroid
  mf     = MeterFrame(center)
  각 자식 정점 v: gl = rotate(mf.toMeters(v_lnglat), −groupRotation)   // 그룹 로컬축
  box    = gl들의 AABB (boxCenterLocal, half)
```

- **회전**: 자식과 프레임이 같은 각도로 도므로 자식은 그룹 로컬에서 **안 움직임** → AABB 불변 → 박스가 **강체로 회전(안 튐)**. (centroid는 자기 기준 회전이라 불변, `rotate(·,−groupRotation)`도 회전에 불변.)
- **스케일**: 박스가 매 렌더 자식을 **tight하게 감쌈 → 안 삐져나옴**. 앵커·스케일 인자는 여전히 **드래그 시작 스냅샷** 기준(출력→입력 피드백 없음).

### 핵심 원칙 (다른 프로젝트 적용 시 추가)
- [ ] **회전각만 지속시키고, 박스 크기·중심은 자식에서 도출**한다. 박스를 매 프레임 저장·재사용하지 말 것.
- [ ] 박스 AABB는 **화면축이 아니라 "회전된 그룹 로컬축"** 에서 잡는다 → 회전에 불변 → 핸들 안 튐 + 항상 tight.
- [ ] 앵커·스케일 인자는 드래그 시작 스냅샷 고정(§2·§3 그대로).

### 알려진 한계 (PPT와의 차이)
- 이 모델은 **자식이 진실의 원천**이고 박스는 도출(shrink-wrap)이다. PPT는 반대로 **박스가 진실의 원천**이고 자식에 full affine(전단 포함)을 적용한다.
- 결과: **축이 정렬된 자식**(회전 0 또는 그룹과 함께 회전) + 어떤 스케일 → PPT와 동일. **자기 회전이 그룹과 다른 자식** + **비균일** 스케일 → PPT는 평행사변형으로 **전단**하지만 이 모델은 자식을 `{scale.x, scale.y}` 2개로만 다뤄 전단을 표현 못 함(모양이 PPT와 다름). 단, **박스가 tight하게 감싸므로 삐져나오진 않음.**
- 완전한 PPT(전단 포함)가 필요하면 자식을 `{center, rotation, scale}`이 아니라 **정점에 2×2 affine을 굽는(bake)** 모델로 바꿔야 한다.

## 7. affine bake — 왜 안 쓰는 게 나은가 + 다른 프로젝트가 쓰는지 판별

> **결론**: 완전한 PPT 전단을 위해 정점에 affine을 굽는(bake) 방식은 **실제로 적용해보니 부작용이 커서 권장하지 않는다.** `{center, rotation, scale}`(유사변환) 모델 + tight 도출 박스(§6)가 더 안전하다.

### affine bake란
자식을 `{center, rotation, scale}`로 두지 않고, **정점 좌표에 2×3 affine 행렬을 매 변환마다 곱해 넣는(굽는)** 방식. 전단(shear)을 표현할 수 있어 회전된 자식이 비균일 스케일에서 평행사변형이 된다(진짜 PPT).

### 부작용 (bake를 피하는 이유)
- **누적 오차·왜곡**: 변환이 기하를 **파괴적으로 덮어씀** → 반복하면 부동소수점 오차가 복리로 쌓여 도형이 점점 찌그러진다. 왕복(resize out→back) 후 원형 복귀가 안 됨.
- **의미 손실**: 한 번 전단되면 그 자식의 "회전각/스케일"이 더는 명확하지 않다 → 인스펙터 표시, 이후 단일 리사이즈의 핸들 축이 비뚤어진다.
- **역변환 불가**: 유사변환 스냅샷이 없으면 "직전 상태로 되돌리기"가 어렵다(회전 버그의 delta 누적과 같은 계열의 함정).
- **직렬화 불일치**: 모델이 `{center,rotation,scale}` 기준이면 bake 후 저장/불러오기에서 의미가 바뀐다.

> 안전한 대안: **유사변환 모델 유지 + 박스는 자식에서 tight 도출**(§6). 전단은 포기하지만 삐져나옴은 없고, 왕복·직렬화가 안전하다.

### 다른 프로젝트가 affine bake를 쓰는지 판별하는 법

**코드 신호 (하나라도 걸리면 bake/affine 의심)**
- [ ] 자식이 `{x, y, width, height, rotation}`(스칼라)이 아니라 **행렬**(`matrix`, `[a,b,c,d,e,f]`, `DOMMatrix`, 3×3) 또는 **변환된 정점 배열**을 저장한다.
- [ ] 변환 핸들러가 **행렬을 곱해 geometry(정점)에 써넣는다** (`points = points.map(p => M.apply(p))`), 스칼라 `rotation/scale` 필드를 갱신하지 않는다.
- [ ] 행렬에 **전단(skew) 성분**이 독립적으로 존재한다(순수 회전이면 나올 수 없는 off-diagonal). 유사변환 모델엔 전단 항이 없다.
- [ ] `bake`, `flatten`, `applyTransform`, `commitTransform`, `matrixMultiply` 같은 이름이 geometry에 대해 호출된다.

**시각 신호**
- [ ] 회전된 자식을 그룹에서 **비균일 스케일**했을 때 자식이 **평행사변형으로 전단**되면 → affine(bake 또는 live) 적용 중. 전혀 전단되지 않으면 → 유사변환 모델.

**bake(파괴적) vs live affine(비파괴적) 구분**
- **live affine**: 원본 geometry + 변환 행렬을 렌더 시에만 적용 → **가역**. 왕복 시 원형 복귀 ✓.
- **bake(파괴적)**: 저장된 geometry 자체를 덮어씀 → **비가역**. 왕복 시 왜곡·드리프트 누적 ✗.
- **판별 테스트(왕복)**: 그룹을 비균일으로 늘렸다가 정확히 되돌렸을 때 자식 기하가 **원형으로 복귀하면 live/유사변환**, **점점 찌그러지면 bake**.

**그쪽 AI에 던질 질문 (복사용)**
1. 자식(도형) 하나를 저장하는 필드가 스칼라 `{x,y,w,h,rotation,scale}`인가, **행렬/정점 배열**인가?
2. 그룹 리사이즈 시 자식의 **rotation/scale 스칼라 필드가 바뀌나**, 아니면 **정점 좌표가 바뀌나**?
3. 회전된 자식을 비균일 스케일하면 **평행사변형으로 전단되나**? (되면 affine)
4. 그 전단 결과가 **원본 geometry에 덮어써지나**(bake), 렌더 시점 행렬로만 적용되나(live)?
5. 왕복(늘렸다 되돌리기) 후 자식이 **원형으로 정확히 복귀하나**?

## 8. 레퍼런스 구현

`map-aabb/src/app/shape-tester.tsx` — MapLibre 맵 위 그룹/단일 도형 변환 테스터.
- `computeGroupBox(sel, rotationDeg)`: 회전된 그룹 로컬 프레임의 tight AABB 도출 (§6)
- 지속 상태 `groupRotation`: 선택 SET 변경 시 0으로 리셋, 그룹 회전 시에만 갱신
- `group-rotate`: 자식은 centroid 기준 회전 + 회전각 갱신, 박스는 다음 렌더에 도출(강체 회전)
- `group-scale`: 그룹 로컬 OBB 리사이즈, 반대편 모서리(anchorLocal) 스냅샷 고정 `P' = A + S·(P₀ − A)`
- 자식 `linear`: 일반 2×2 live affine 행렬. 혼합 회전 자식의 비균일 그룹 스케일에서 필요한 전단을 비파괴적으로 보존
- 카메라 입력: 평상시 pitch/bearing 허용, 도형 변환 중에만 임시 잠금하고 완료·취소 시 이전 상태 복구
- 맵: 초기 `pitch: 0`은 유지하지만 pitch/bearing 조작은 허용한다. 따라서 §2의 평면 고정 가정에만 의존하지 말고, 회전·기울기 상태에서도 `project`/`unproject`와 그룹 로컬 OBB의 앵커 고정을 검증해야 한다.
- 단일 도형: 도형 자신의 로컬 프레임(OBB) 기준 — 회전돼도 자기 프레임이 일관되어 정상 (그룹도 이와 동일한 원리를 프레임 상태로 부여한 것).

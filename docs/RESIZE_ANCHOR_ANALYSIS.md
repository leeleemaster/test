# 그룹 선택상자 리사이즈 버그 — 분석 절차

> **증상**: 그룹 선택상자의 **bottom 핸들을 줄였는데** ① left·top·right가 **전체적으로 같이 줄어들고**, ② 도형 **전체 위치가 움직인다**. (회전은 Finding #2로 정상화된 상태)
> **이 문서**: 원인 후보를 판별하는 **분석 절차**. 순서대로 실험하면 원인이 갈라진다.
> 관련: `ROTATION_FIX_FINDINGS.md`(회전 확정 원인), `ROTATION_FIX_PROPOSAL.md`(계약 설계).

---

## 0. 깨진 불변식 (기준부터)

> **리사이즈 불변식**: 핸들 H를 드래그하는 동안, **반대편 앵커 A는 화면에서 한 픽셀도 움직이면 안 된다.**
> (bottom 드래그 → top 변 고정. corner 드래그 → 대각 corner 고정.)

올바른 공식 — **모든 점(자식 정점 + 그룹 center 포함)** 에 대해:

```
P' = A + S · (P − A)          S = diag(sx, sy)
                              edge 핸들: 한 축만 ≠ 1 (bottom → sx=1, sy=h'/h)
                              corner 핸들: 두 축 (비율 고정이면 sx=sy)
```

- center+로컬좌표 모델에서 자식만 `S·P`로 줄이면 → **중심 기준 수축** (앵커 안 고정)
- center 이동 보정(`center' = A + S·(center−A)`)을 빠뜨리거나 부호/프레임을 틀리면 → **위치 드리프트**

## 1. 증상 분해 — 신호 2개는 서로 다른 원인

| 신호 | 관찰 | 의미 |
|---|---|---|
| **A** | bottom만 줄였는데 4변이 다 줄어듦 | 스케일이 **균등 스칼라**(양축)로, **중심 피벗**으로 적용되는 중 |
| **B** | 전체 위치가 이동 | 순수 중심 피벗이면 중심은 제자리여야 함 → **별도 원인**: 앵커 보정 부호/프레임 오류 or 드래그 중 재계산 피드백 |

## 2. 용의자 순위 (그쪽 구조 기준)

- [ ] **1순위 — 회전 피벗 재사용**: 회전 수정에서 그룹 피벗 = selectionframe **center**로 정리됨. 리사이즈가 같은 `transformGroup*` 계열 기계를 타며 **회전용 중심 피벗을 스케일 피벗으로 재사용** 중일 가능성. **회전=중심 피벗이 맞지만, 리사이즈=드래그 반대변 피벗** — 두 연산의 피벗 계약이 다르다.
- [ ] **2순위 — 균등 스케일 API**: bottom 드래그로 `newHeight/oldHeight`를 구해 **스칼라 하나짜리 `setScale(s)`** 에 넣어 양축 적용. edge 핸들은 반드시 `(sx, sy)` 분리.
- [ ] **3순위 — 앵커 보정의 Y부호/프레임 오류** (회전 버그와 같은 계열): `center' = A + S·(center−A)` 보정을 screen(Y-down)에서 계산해 model(Y-up)에 적용 → center가 반대 방향 이동 → 드리프트. 이 프로젝트에서 이미 두 번 확인된 반사 불일치 패턴.
- [ ] **4순위 — 드래그 중 피드백 루프** (delta 누적의 리사이즈판): 매 pointermove마다 증분 스케일 적용 + **스케일된 결과로 bbox/anchor 재계산** → 오차·이동 누적. 스냅샷(드래그 시작 bbox·anchor 고정) 기반이어야 함.
- [ ] **5순위 — (회전된 그룹일 때만) 축 불일치**: screen bbox의 "bottom"은 회전된 그룹의 로컬 bottom이 아님. screen-Y만 줄였는데 로컬에서 x·y 성분으로 분해 → 양축 변화 + 이동.

## 3. 판별 실험 절차 (이 순서대로 — 각 실험이 용의자를 갈라냄)

### 실험 1 — 회전 0°에서 bottom 드래그
- [ ] **중심 고정 + 4변 대칭 수축** → 중심 피벗 + 균등 스케일 (**1·2순위 확정**, 위치 이동은 별도 원인 계속 추적)
- [ ] **top 고정, left/right만 줄어듦** → 균등 스케일만 (**2순위 단독**)
- [ ] **전체가 한 방향으로 밀림** → 보정 부호 오류(**3순위**) 또는 피드백(**4순위**)

### 실험 2 — 왕복(jiggle) 테스트
- [ ] 아래로→위로→아래로 드래그해 포인터를 **시작점에 되돌렸을 때**:
  - 도형이 원래 크기·위치로 **안 돌아옴** → 증분 누적/피드백 (**4순위 확정**)
  - **돌아옴** → 스냅샷 기반, 4순위 제외

### 실험 3 — 45° 회전 후 재시도
- [ ] 0°에서는 정상인데 **회전 상태에서만** 깨짐 → 축 불일치 (**5순위 확정**)
- [ ] 0°에서도 동일하게 깨짐 → 5순위 제외 (1~4순위 중)

### 실험 4 — 코드 직접 확인 2개
- [ ] 리사이즈가 호출하는 **스케일 API 시그니처**: 스칼라 `s` 하나인가, `(sx, sy)` 인가?
- [ ] **피벗 인자**: selectionframe center인가, 드래그 핸들의 반대변인가?

### 실험 5 — (3순위 의심 시) 보정 벡터 부호 확인
- [ ] 드래그 한 프레임에서 `A_기대(고정이어야 할 앵커)` 와 `A_실제(적용 후 앵커)` 를 로그로 비교.
  - `A_실제`가 기대와 **반대 방향으로 2배** 이동 → 보정이 역부호 (Y-flip 계열)
  - `A_실제`가 center 쪽으로 끌려감 → 보정 자체가 없음 (중심 수축)

## 4. 그쪽 AI에 던질 질문 (복사용)

아래 질문에 각 1~2줄, 가능하면 코드 한 줄로 답해줘.

1. 그룹 리사이즈의 스케일 피벗은 무엇인가? (selectionframe center / 드래그 핸들의 반대변 / 기타) — 해당 코드 붙여줘.
2. edge 핸들(bottom 등) 드래그 시 스케일 인자는 **스칼라 1개**인가 **(sx, sy) 2개**인가?
3. 스케일 적용 시 그룹 **center(위치)도 함께 변환**하나? 한다면 그 공식은? (`center' = A + S·(center−A)` 형태인지)
4. 드래그 중 bbox/anchor를 **드래그 시작 스냅샷**으로 고정하나, **매 프레임 재계산**하나?
5. 스케일 인자 계산 프레임(screen/local)과 적용 프레임(screen/local)이 같은가? 회전된 그룹에서도?
6. 리사이즈가 회전과 **같은 transformGroup 계열 함수**를 공유하나? 공유한다면 피벗 인자는 어디서 오나?

## 5. 올바른 알고리즘 스케치 (수정 시 참조)

```
onResizeStart(handle):                     // 스냅샷 — 이후 드래그 내내 불변
  bbox0   = 현재 그룹 bbox (그룹 로컬 프레임)
  A       = handle의 반대변/반대corner (그룹 로컬)
  h0      = handle 시작 위치 (그룹 로컬)

onResizeMove(pointer):
  p       = pointer를 그룹 로컬로 역변환    // 회전 해제 포함 — 축 불일치(5순위) 방지
  sx, sy  = 축별 인자: (p − A) / (h0 − A) 를 핸들 종류에 맞는 축만
  각 자식: P' = A + S·(P0 − A)             // P0 = 스냅샷 좌표 (증분 누적 금지)
  center' = A + S·(center0 − A)            // 이 줄이 앵커 고정의 핵심

onResizeEnd:
  commit (base 갱신), 스냅샷 폐기
```

핵심 계약 3개:
- [ ] **피벗 = 드래그 반대변** (회전의 중심 피벗과 다른 계약 — 공유 금지)
- [ ] **edge는 축별 인자** (스칼라 균등 금지)
- [ ] **스냅샷 기준 절대 계산** (증분 누적·드래그 중 bbox 재계산 금지 — 회전의 절대각 원칙과 동형)

## 6. 기존 발견과의 관계

- 3순위(보정 부호)와 5순위(축 불일치)는 **회전 버그와 같은 뿌리**(프레임/반사 계약 불일치)의 리사이즈 발현 — `ROTATION_FIX_PROPOSAL.md` §2 계약이 리사이즈에도 그대로 적용된다.
- 4순위(증분 피드백)는 회전의 "delta 누적" 원칙 위반과 동형 — **스냅샷 기준 절대 계산**이 해법인 것도 동일.
- 1순위(피벗 재사용)는 새 교훈: **연산마다 피벗 계약이 다르다** (회전=중심, 리사이즈=반대 앵커). 회전 수정에서 center 피벗을 강화한 것이 리사이즈에 부작용을 냈을 수 있음 — 회전 수정 커밋 전후로 리사이즈 동작이 달라졌는지 이력 확인 가치 있음.
- 참고: 레퍼런스(`map-aabb`)는 리사이즈 핸들 미구현(문서화된 한계)이라 데모 대신 **5장 알고리즘**이 기준.

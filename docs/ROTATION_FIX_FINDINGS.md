## Finding #1 — rectangle.ts의 `-angle`은 땜질이 아니라 "필요한 프레임 변환"일 가능성이 높음

**날짜**: 2026-07 | **출처**: 그쪽 프로젝트 정적분석 | **상태**: ✅ 해결 — Finding #2에서 확정 (guide의 변환은 필요한 것이 맞았고, 실제 원인은 bake 누락 + 커밋 이중 반전)

### 발견 내용
정적분석 결과, `rectangle.ts`의 `-angle`은:
- **mercator Y-up delta 누적 프레임** (회전 delta가 누적되는 공간)
- **실제 screen Y-down geometry bake 프레임** (geometry가 구워지는 공간)

이 **두 프레임을 잇는 필요한 변환**일 가능성이 높다. **지금 지우면 오히려 새 버그를 만든다.**

### 판정 — 기존 사전 분류를 뒤집음
- 기존 워크시트 사전 분류: "(a) 프레임 보정 유력 → 제거 방향" ❌
- **갱신된 판정: (a-2) — 필요한 변환이 익명 인라인으로 존재.** 삭제 금지.
- 수학적 근거: Y-up ↔ Y-down 두 프레임이 실재하는 이상, 그 사이 부호 변환 **1회는 반드시 필요**하다(반사 홀짝). 그 유일한 변환을 지우면 반사 수가 홀수로 틀어져 방향이 뒤집힌다.

### 처방 — 삭제(deletion)가 아니라 승격(promotion)
| | 잘못된 처방 | 올바른 처방 |
|---|---|---|
| 행동 | `-angle` 삭제 | **부호는 유지**, 이름 있는 경계 변환 함수로 **위치만 이동** |
| 성격 | 동작 변경 (새 버그) | **동작 보존 리팩터** (렌더·저장값 완전 불변) |
| 문제의 재정의 | "부호가 있는 것"이 문제 | "부호가 **이름 없이 도형 파일 안에** 박혀 아무도 의미를 모르는 것"이 문제 |

승격 예시: `-angle` → `accumFrameToBakeFrame(angle)` (또는 `screenAngleToModel` 계열) — 의미가 이름에 드러나는 단일 변환 함수로 추출.

### 확정 절차 (승격 전 반드시)
- [ ] **홀짝 카운트**: 그 `-` **없이** 측정→저장→적용→bake 파이프라인의 Y 반사(부호 반전)를 전부 센다.
  - **홀수** → (a-2) 확정: 그 `-`가 필요한 변환. **승격** 진행.
  - **짝수** → 어딘가 **두 번째 반전**이 존재(서로 상쇄 중). (a-1) 중복 케이스 — 짝을 찾아 **둘을 함께** 정리해야 함. 하나만 건드리면 깨짐.
- [ ] 승격 커밋은 **골든(수치+스크린샷)으로 완전 불변 증명** 후 머지.

### 파급 효과
- [ ] `ROTATION_FIX_IMPLEMENTATION.md` 1장: (a)를 **(a-1) 중복 보정(삭제) / (a-2) 필요한 변환(승격)** 으로 분리 — 반영 완료.
- [ ] 사전 분류표 rectangle 행: (a) 유력 → **(a-2) 유력, 삭제 금지** — 반영 완료.
- [ ] 5장 마이그레이션: 승격은 동작 보존이므로 **저장값 불변 → `s_rect = +1` 유력** (골든 비교로 최종 확정).
- [ ] **다른 도형에도 같은 질문 적용**: ellipse/arc/sector의 반전 경로도 "중복(a-1)인가, 유일한 변환(a-2)인가"를 각각 홀짝 카운트로 판정할 것. rectangle이 (a-2)였다면 **다른 도형의 반전도 (a-2)일 개연성이 올라간다** — 일괄 제거 금지 원칙(§8-1)이 실코드로 재확인된 셈.

### 교훈 (설계 문서와의 관계)
원래 설계의 "부호를 각도에서 없애라"는 문장의 정확한 의미가 실코드로 확인됐다:
> 부호를 **없애라**가 아니라, 부호를 **익명 땜질에서 이름 있는 경계 변환으로 옮겨라**.

rectangle의 경우 그 변환이 (이름만 없을 뿐) 이미 올바른 자리에서 올바른 일을 하고 있었다. 버그의 원인은 이 변환 자체가 아니라, **이 변환의 존재를 모르는 다른 경로들**(delta 누적·읽기 쪽·다른 도형)이 계약을 어기는 데 있을 가능성이 높다 — 수사 방향을 그쪽으로.

## Finding #2 — 확정 원인과 실제 수정: bake 누락 + 커밋 이중 반전 (그룹 회전 정상화 ✅)

**날짜**: 2026-07 | **출처**: 그쪽 프로젝트 실코드 수정·검증 | **상태**: ✅ rectangle 그룹 회전 정상화 확인

### 확정된 원인 (두 증상의 실체)
1. **guide는 옳았다**: 선택상자 guide는 `selectFigureModify`에서 이미 `screenGuideRotation = -guideRotation` (map 모드)로 **올바르게 부호를 변환해 그리고 있었다**.
2. **어긋남(증상 ①)의 원인 = bake 누락**: 실제 도형 geometry를 굽는 `rectangle.ts`의 `applyRectangleGeometry`에는 **이 변환이 빠져** 있어 guide와 다른 각도로 그려졌다.
3. **급점프·방향 반전(증상 ②)의 원인 = 커밋 이중 반전**: 회전값을 저장하는 `transformGroupRotateAngle`은 `applyGroupGuideRotateIntent`가 **이미 guide와 연속적인 값을 넘겨주는데도 불필요하게 한 번 더 부호를 뒤집고** 있었다.

### 적용된 수정 (2건)
| 위치 | 수정 | 효과 |
|---|---|---|
| `rectangle.ts` `applyRectangleGeometry` | map 모드 geometry bake에 **guide와 동일한 부호 변환 추가** (`screenRotation = -rotation`) | guide와 도형이 같은 각도로 맞물림 |
| `rectangle.ts` `transformGroupRotateAngle` | **불필요하게 부호를 뒤집던 override 삭제** (기본 동작 복귀) | 급점프·방향 반전 해소 |

→ **그룹 회전 정상화 확인됨.**

### 프레임워크 검증 — (a-1)/(a-2)/홀짝 체계와 정확히 일치
- guide의 `-rotation` = **(a-2) 필요한 변환** → 유지됨 (Finding #1의 "삭제 금지" 판단이 옳았음)
- bake의 변환 **누락** = 그 경로만 반사 홀짝이 모자람 → 같은 변환을 **추가**해 홀짝을 맞춤
- 커밋의 **이중 반전** = **(a-1) 중복** → **삭제**
- 즉 세 경로(guide/bake/commit)가 **서로 다른 반사 횟수**를 갖고 있던 것이 근본 원인. "경로마다 같은 각도 계약"(§9-1·§9-2)이 실코드로 증명됨.
- 증상 ②의 실제 기제도 정정: delta 누적 자체보다 **연속 intent 값 위에 커밋이 여분의 반전을 얹은 것**이 급점프의 원인이었다.

### 우리(map-aabb) 코드 반영
- 우리 레퍼런스는 guide(SVG 오버레이)와 mesh(Three)가 **같은 변환을 공유**하므로 "bake 누락"에 해당하는 지점이 없음.
- "커밋 이중 반전 삭제 + 연속 절대각 그대로 사용"은 정상 경로가 이미 그 형태 → **재현 토글 기본값을 OFF(수정 반영)로 전환**, 재현 브랜치(수정 전 동작)는 회귀 비교용으로 유지.

### 남은 확인 (그쪽 프로젝트)
- [ ] **저장 호환성(리스크 0순위)**: `transformGroupRotateAngle`의 반전 삭제로 **저장되는 회전값의 부호 의미가 바뀌었을 수 있음** — 수정 전 저장한 v1 골든 파일 로드가 동일하게 열리는지 라운드트립 필수. 바뀌었다면 마이그레이션 상수 `s_rect = -1` 적용.
- [ ] **다른 도형 동일 패턴 점검**: ellipse/arc/sector에도 "guide는 변환 있음 / bake는 누락 / commit은 중복" 같은 **경로별 반사 불일치**가 있는지 — 도형별 3경로(guide/bake/commit) 반사 카운트 비교로.
- [ ] **단일 선택 경로**: 이번 수정은 그룹 회전. single fast path(rectangle-screen 분기 등)도 같은 3경로 점검 필요 (리스크 5).
